When I first set up authentication for focuswaqt, I went with Supabase. It seemed like the obvious choice. Managed Postgres, built-in auth, one dashboard.

Then I looked at the URL my users were being redirected to after signing in with Google.

It was a 200-character string of random characters. JWT payload, base64-encoded, sitting in the browser address bar. Technically harmless. But it looked phishing-adjacent. Not exactly the impression you want to make on first login.

That was my nudge to look at alternatives.

## Why I Moved Away from Supabase Auth

Supabase Auth isn't bad. But for my use case, it had a few problems.

The long redirect URLs were the first thing I noticed. Supabase encodes the entire session token into the callback URL, which works but looks suspicious to users who pay attention to their address bar.

The bigger issue was data ownership. Supabase Auth stores users in its own internal schema, separate from your application tables. Want to join a user with your `profiles` table? You're querying across two different ownership models. It works, but it's friction.

And then there's the pricing question. Supabase's free tier is generous, but once you're on a paid plan, you're paying for a lot of infrastructure you might not need if all you want is Google OAuth and sessions.

## What Better Auth Gets Right

Better Auth stores everything in your own database. Users, sessions, accounts — they're all just tables in your Postgres instance. You own them completely.

The session token is a short opaque string stored in an httpOnly cookie. No JWT in the URL. No strange-looking redirect. Just a clean redirect to `/app` after OAuth.

It's also built specifically for Next.js App Router. Server Actions, `headers()`, middleware — it all works the way you'd expect.

## The Actual Setup

Here's what the configuration looks like in practice.

**Install the packages:**

```bash
npm install better-auth
```

**Create your auth config** at `lib/auth.ts`:

```typescript
import { betterAuth } from 'better-auth';
import { Pool } from '@neondatabase/serverless';

export const auth = betterAuth({
    database: new Pool({ connectionString: process.env.DATABASE_URL }),
    socialProviders: {
        google: {
            clientId: process.env.GOOGLE_CLIENT_ID!,
            clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
        },
    },
});
```

**Create the auth client** at `lib/auth-client.ts`:

```typescript
import { createAuthClient } from 'better-auth/react';

export const authClient = createAuthClient({
    baseURL: process.env.NEXT_PUBLIC_APP_URL,
});
```

**Add the API route** at `app/api/auth/[...all]/route.ts`:

```typescript
import { auth } from '@/lib/auth';
import { toNextJsHandler } from 'better-auth/next-js';

export const { GET, POST } = toNextJsHandler(auth.handler);
```

That's the full setup. Better Auth creates the `users`, `sessions`, and `accounts` tables automatically on first run.

## Using Sessions in Server Actions

This is where App Router integration matters. In a Server Action, you get the session like this:

```typescript
import { auth } from '@/lib/auth';
import { headers } from 'next/headers';

export async function updateStreak() {
    const session = await auth.api.getSession({ headers: await headers() });

    if (!session?.user) return { success: false, error: 'Not authenticated' };

    // session.user.id is your user's ID
    // same ID that lives in your profiles table
}
```

No client-side token passing. No JWT decoding. Just `headers()` and you have the session.

## Extending the User with a Profiles Table

Better Auth creates a `users` table. Your app data lives in a `profiles` table that references it. The schema looks like this:

```sql
CREATE TABLE profiles (
    id TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    current_streak INTEGER DEFAULT 0,
    longest_streak INTEGER DEFAULT 0,
    last_study_date DATE,
    updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

When a user signs in for the first time, create their profile via a Better Auth hook:

```typescript
export const auth = betterAuth({
    database: new Pool({ connectionString: process.env.DATABASE_URL }),
    socialProviders: { google: { ... } },
    hooks: {
        after: [
            {
                matcher: (context) => context.path === '/sign-in/social',
                handler: async (context) => {
                    const userId = context.context.newSession?.userId;
                    if (userId) {
                        await sql`
                            INSERT INTO profiles (id)
                            VALUES (${userId})
                            ON CONFLICT (id) DO NOTHING
                        `;
                    }
                },
            },
        ],
    },
});
```

Now every Server Action has direct access to streak data, task data, and any other profile fields through the same Neon connection pool. One database. No cross-service queries.

## The Redirect That Actually Makes Sense

The original Supabase setup had `callbackURL: '/'` which created a race between the OAuth cookie being written and the middleware redirect. Users sometimes ended up back on the landing page instead of the app.

Better Auth with a direct `callbackURL: '/app'` just works:

```typescript
await authClient.signIn.social({
    provider: 'google',
    callbackURL: '/app'
});
```

Short token in a cookie. Clean redirect. No 200-character URLs that look like they belong in a phishing email.

## What Changed After Switching

The codebase got simpler. Session checks are one function call. The database is one Postgres instance on Neon. There's no separate auth service to configure, no Supabase dashboard to maintain alongside the app.

The biggest thing I didn't expect: better observability. When something goes wrong with auth, I can query the `sessions` table directly. I can see exactly when a session was created, when it expires, which device signed in. With Supabase Auth, that data was behind their dashboard.

If you're building a Next.js 15 app and want auth that lives in your database and doesn't make your redirect URLs look suspicious, Better Auth with Neon is the right call.
